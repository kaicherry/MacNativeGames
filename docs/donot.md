These are this project's own paid-for faults, appended as they are met; a listed fault that repeats is a defect in whatever repeated it.
1. **Do not symlink a fixture `.venv` to `sys.prefix` when tests invoke `.venv/bin/python`.** The prefix may contain only a versioned executable such as `python3.14`, leaving the unversioned path absent. Create the fixture's `.venv/bin/python` and link it to `sys.executable`.
2. **Do not hash the whole multi-GB NSP.** `shasum -a 256` over the 7.39 GB `game.nsp` exceeds the 120 s shell limit and returns nothing, so the attempt buys no number and loses the window. Use the per-file ExeFS hashes and the Program NCA identity; a whole-package digest needs a longer, explicitly-sized run.
3. **Do not conclude a structure is absent from raw container bytes.** NCA3 headers are AES-XTS(`header_key`) and their section bodies are AES-CTR, so `NCA0`, `CNMT` and `NACP` never appear before decryption; S1.1 recorded "no `NCA0` at `0x200`" and S1.2 "the meta artifact holds no CNMT", and S1.3a then found the file S1.1 had kept all along. Decrypt first. Two offsets follow from the same layer: a section's PFS0 starts at its `pfs0_offset` (past the hash table), not at the section start, and `display_version` is a NACP field, not a CNMT one.
4. **Do not blanket-rename a forked tree's comments to the new game's name.** The comments record what was measured on the predecessor ("Bayonetta 3 does X; TOTK never calls it"); renaming them silently turns those measurements into unverified claims about the new game. S1.3's fork rename did exactly that across `games/nfs/` and the claims were walked back to their true subject. Rename a comment's game name only when the statement is re-observed on the new game; otherwise keep the predecessor's name as the attribution.
5. **Do not let one `runtime_fail` cover several calls.** S1.3's `FAIL: native display link initialization` wrapped three `CVDisplayLink` calls in one condition, so its record can never say which returned -6661 and S2.1's probe could only attribute the failure to the environment, never to a call. Log each call's own code at the site; the message names the symptom and the record needs the cause.
6. **Do not read an SDK descriptor field as data before checking that the game initialises it.** `AudioOutBuffer.data_offset` held `0xcdcdcdcdcdcdcdcd` because the title leaves the field unset while the SDK copies the whole 0x28-byte struct; the host's `data_offset + data_size <= capacity` then failed on a value that was never an offset, and the boot stopped for a whole slice. Validate the field's own range: an offset past the buffer's capacity cannot be an offset, so treat it as zero and log the correction once. The same applies to any struct the SDK copies in full — fill patterns are not data.
7. **Do not call a log bilingual because its source comments carry an English sentence.** The host text has 61 `TOTK_UI("中文","English")` pairs, but 250 `MLOG` strings and 44 `fprintf` sites emit Chinese only; the operator was told the logs were "bilingual by design" and then could not read the boot log. Say which emitted strings are English and which are not, and check the string, not the comment.
8. **Do not name a stall by the frame one run happened to stop at.** S2.6 recorded "presenting stops at frame 600" from boot2 while boot1 stopped at 354; the S2.7 boots stopped at 399 and 354. A stop seen at different frames is not pinned to the highest one. Report the range and the runs, and let the diagnosis name the trigger.
9. **Do not model a virtual core without rotating equal-priority threads.** The runtime preempted only for strictly higher priority, so in S2.9 a worker spinning on a shared core starved the woken main thread for the entire 2.6 s present gap (`core waiter 0x1001`, `core 0 owner 0x1002 for 2641.8 ms`, `0x1d x10908312`), and two more threads queued on a critical section the starved thread owned. A woken sibling that can only run on that core is the same as no wakeup; the time slice at the SVC checkpoint is what makes the wakeup real.
10. **Do not rest a probe's attribution on a separate control run.** S2.11 pressed ⊕ in run P and the picture went from the `PRESS ⊕` title screen to a save-data notice; the control run that was to make that attributable stopped presenting at 39.7 s, before its first capture, so it reached none of the comparison window and wrote no PNG. The claim then had to rest on the probe run's own before-capture (the prompt up three seconds earlier), the attract loop's known screens and the new screen's own different button — a control that dies before the window is not a control. A single run can carry its own baseline: capture it before the input.
11. **Do not close a slice by appending its record while the STATE.md top sections still name the finished slice.** S2.9's close appended its section but left "Where the work is", "Next action", "In progress" and "Queued" at S2.9; S2.10's close corrected them and said so in its commit body, and S2.11's close then repeated the slip — after `5994c6d` the top sections still said S2.11 was next and the summary still said the guest had not been observed to react to input, so the S2.12 session had to work out the state it was actually in. Advance all of them — "Where the work is", "Next action" + gate + closes-when + Do-Not count, "Completed", "In progress" and "Queued" — in the same commit as the record.
12. **Do not name a stall's cause from a trace window that ends after the stall began.** S2.12's ring held 128 condition events — 0.6 s of the four frame workers' churn — while its dump lands 2.6 s after the stop begins, so "no signal event appears in any of r4's three rings" described the stuck state and said nothing about the transition that caused it, and the S2.13 board was written on that sentence. S2.13 widened the ring to 16384 entries (dumping the last 4096, 3.9 s in the stopped run) and caught the transition on the first stop it reproduced: main's last kick to the frame workers and its unmatched completion wait, 2.58 s before the dump. Size a stall's window from the stop's own lateness, not from the dump.

13. **Do not read a counter that fires on the healthy path as evidence of the fault.** S2.14 built two candidates for the frame-completion credit's thief — `rewait` (a waiter woken for a credit that then waited again with no release since) and `unattributed` (a count drop first seen at a wait) — and in 13 clean 65 s boots both read at or near *every* blocking acquire on every completion semaphore (r1 `…b18` rewait 2295 / unattributed 6533 of 7026 acquires; `…b28` 2351 / 2145 of 2360; `…d58` 1550 / 1562 of 1564). Both fire on the healthy loop, because a take that *succeeds* also leaves no event: between two observations every take looks unattributed, and a waiter that took its credit and came back for the next one looks re-woken. The hypothesis they would have confirmed — S2.13's "a worker must be taking those credits through `TryAcquireSemaphore`" — was withdrawn instead by the one measurement that separates the cases, the account itself: on every completion key the surplus of releases over blocking acquires equals the waiter's own releases and the workers' releases equal the waiter's blocking acquires, with the workers' own acquires at zero, in 13 of 13 runs. A counter must fire only on the fault; check a new counter against the healthy case before it is trusted.
14. **Do not read a stop rate or a frame count taken while another local process held the GPU as a property of the build.** S2.14's first instrumented batch measured 7 stops in 20 boots and a boot reaching frame 1375–1803 by 65 s, against S2.13's uninstrumented 1 in 20 and 1651–1853, and the instrument was about to be recorded as a load that raises the stop rate and costs ~20% of the frames. Another local process held the GPU for that batch. With the GPU free the same binary, instrument and all, ran 13 boots with zero stops and frames 1851–1855 — indistinguishable from the uninstrumented baseline. A rate is a property of the machine as much as of the build: discard such a batch rather than report it, and compare a rate only against a baseline measured the same way. The discarded batch is kept at `.babysteps/scratch/S2.14-credit-trace/gpu-contended/` and is named as discarded.

15. **Do not read a release/acquire balance as naming who took a credit.** S2.14's account — on each frame-completion semaphore the surplus of releases over blocking acquires equals the poster's own releases, and the workers' releases equal the poster's blocking acquires — was recorded as proof that "no credit is taken by a third party", and S2.13's hypothesis was withdrawn on it. Both sides of that identity are invariant to who takes the credit: it holds whether the poster re-acquires its own post or a third thread takes it and the poster waits for a replacement. The identity bounds the account; it cannot attribute. S2.15 made the take visible (the SDK's three count stores trap to the SIGILL handler, which performs the store and records the taker) and the conclusion held — the three frame workers' `take` is 0 on every completion key in 12 of 12 runs — but only the trap could show it, and a slice was spent re-establishing what the balance had been read as settled. Attribute a take from an observation of the take, not from a balance.

16. **Do not read a zero-hit `search_text` as absence.** S2.16 had to know whether this tree issues `ReleaseSemaphore`, and `search_text` answered `result_count: 0` for `semaphore`, `Semaphore`, `take` and `runtime_game_patches` alike — every query tried, including a string the tree holds in 22 files (`games/nfs/runtime/game_patches.c` is titled with `semaphore`). The tool's own reply carries `absence_evidence: {"citable": false, "blocked_by": "the index did not cover the whole tree at scan time"}`, so it disclaims its own empty answer in the same breath, and the read was one sentence from recording "the runtime never releases the semaphore". `search_symbols` against the same repo id answers normally, which is what makes the empty text result look like a fact about the tree rather than a fact about the index. Confirm a zero-hit index query from the file itself before it becomes a claim.
17. **Do not name main's own call by the SDK function an unwind frame reaches.** S2.13 recorded main's parking frame as `nn::os::AcquireSemaphore (sdk+0x33b8e0)` through `main+0x743c10`, and S2.17 then built S2.18's first instruction on it — "name `nn::os::ReleaseSemaphore` (`sdk+0x33ba80`) in main's import table, find its thunk and every `bl` to it" — which cannot be executed: main's import table holds **no** `nn::os` semaphore at all (`objdump -R main.elf | grep -i semaphore` prints nothing; the 42 `_ZN2nn2os*` JUMP_SLOT imports are the event/timer/thread/mutex/condition-variable set, and `main-inventory.json`'s `imports` agree). `main+0x743c10` is `bl 0x7f3960` = musl `sem_wait` (GOT `0xd21450`), and the SDK's `sem_wait` (`sdk+0x51bc28`) is what calls `nn::os::AcquireSemaphore` — the SDK body was on the stack, one link below the imported wrapper main actually calls. When a frame or a record names an SDK function, check main's own relocation table for the symbol main imports; the imported wrapper and the SDK body it reaches are different call sites.

19. **Do not treat a work tree as the repo.** The operator's windowed runs and S2.20's evidence boot were built from `/Volumes/X9BS/externalTmp/MacNativeGames/nfs-work`, an `rsync -a` snapshot of `games/nfs` taken 2026-10-22 19:43; 34 files had drifted since, including a `threads.c` with no S2.9 core rotation and no S2.13–S2.15 take trap. Nothing in the log could show it: `rsync -a` preserves the repo's mtimes, so the sources read as older than the binary and `make runtime` says "nothing to be done". A run offered as "the port" must be built from the repo — re-`rsync` with `build_app.py`'s excludes, then force it (`rm -rf build/obj build/nfs-native`) because the preserved mtimes hide the drift.

20. **Do not read the absence of a sound as a broken path without measuring the signal.** Told the game had no audio, the reply named it — "the game is mixing silence" — from the operator's report and a log that opens and starts the queue; one `NFS_AUDIO_TRACE` line then showed the mix live and loud (`peak` 0 for the first ~12 s, then up to 22512, with `played` draining in step), because the attract loop's opening screens are silent. Measure the samples before naming the path broken, and use `afplay` on the same device to split host from port first — it costs one line.

18. **Do not gate a slice's close condition behind a prohibition on the evidence that condition demands.** S2.20's seed said bounded boots "only if a fix follows" while its own close condition required each of the 8 translated shaders to be shown "reached by a submission that presented" — which only a boot could show, because the run that names the 8 (S2.4c/S2.5) ran with `TOTK_GPU_ALLOW_SUBMIT` off (`GPU p50 0.00 ms`) and every run that presented logged no translation for them. The slice stalled on a decision the seed should have made, and the operator had to resolve it; one 90 s boot with a fresh `TOTK_SHADER_CACHE` then named all 8 inside frame 2, which presented at `GPU 0.9 ms`. Write the gate for the evidence the close condition actually needs, or write the close condition to what the gate allows.
21. **Do not read the presses a session's log shows as the presses it made.** `runtime/input.c`'s `user_input()` logs at most once a minute (`60000000000` ns), so the operator's windowed run that reached the `pctl` open shows one `[input] user input` line before its save mount and none between the mount and the open, and neither the count nor the gap is a fact about the presses. S3.1a read that ordering as "the open follows the mount automatically", then spent two repo-built boots (a 140 s Ⓐ schedule and a 200 s fourteen-button sweep) not reproducing it: the game ran to the bound at exit 124 with no stop and no open, while the recorded runs reached it. Attribute a stop to the state the session reached, not to the presses its log happens to show.
22. **Do not read a scripted schedule's failure to reproduce a live session as a fact about the buttons.** S3.1a spent three repo-built boots (two schedules, 25 presses) concluding the `pctl` open was not reachable from `TOTK_INPUT_FILE`, while the three runs that reached it were driven by real window/controller input. The measured difference is `TOTK_HEADLESS`, not the input source: the same binary and the same `TOTK_INPUT_FILE` schedule opened the four `pctl` ports windowed and opened none headless, and `TOTK_AUTOLOAD` was unset in every run — `runtime/autoload.c:28` returns before autoload can steer anything, and no run logged `[autoload]`. S3.1b first wrote this entry as autoload and `TOTK_INPUT_SCRIPT`; the logs carry no `[autoload]` line, and a same-schedule headless control reached neither the save mount nor the open. Before concluding that a scripted stand-in cannot reach a state, change one variable at a time and name the run that shows it.
23. **Do not answer a command that returns an object with a result-only reply.** The `pctl` factory's `CreateServiceWithoutInitialize` returns an `Out<SharedPointer<IParentalControlService>>`; the handler answered `rc 0` with a 4-byte zero datum and no object, and the SDK — reading result 0 as success — stored the null object and dereferenced it at `sdk+0x3489dc` (`fault=0x0`, `esr=0x92000006`). A result and a returned value are two fields: the reply must carry the object (a moved session in `rs->move[]`, which `dispatch`'s domain branch turns into an object id) or the command must fail. `rc 0` with nothing behind it reads as success to a client that then dereferences what it asked for, so check a handler's reply shape against the SDK proxy that sends the command — `sdk.patched.bin` names both, `w3`/`w1` in `_nn_sf_sync_*` is the command id.

24. **Do not build the `b-<chain>` bundle to stop a dev-tree boot compiling its shaders.** `shader_load` (`nvn_mtl.m:4985`) reads a variant's own MSL from `build/shader-cache/rt-<chain>` first and falls back to the `b-<chain>` bundle (`nvn_mtl.m:4630`) only when that file is absent, so a bundle built from the `rt-` cache is never consulted for the very keys it was built from — and route B's shader map has 0 entries in this tree, so it could never have been consulted at all. S2.26's seed named the bundle as the fix; read first, the change would have been inert. The live route is `build/shader-libs/<SHA-256 of the MSL>.metallib` beside the executable (`:4977` `shader_lib_prebuilt`, consulted at `:4992`), which `make shader-libs` (`games/nfs/scripts/build_shader_libs.py`) now writes from the `rt-` cache. Before producing a second copy of anything, read the lookup that consumes it and the order of its preferences.

25. **Do not lower a periodic line's cadence and call the total reported.** S2.27 lowered the per-submit pipeline-wait summary's period from every 100 prediction scans to every scan and it still printed nothing, because the counter the line is gated on (`g_pp_scans`) stayed 0: a bounded windowed attract-loop boot builds all 502 render pipelines in the warm-up, so no pipeline miss reaches `pso_get`, the prediction path never runs, and the counters it reports never advance — a play run only engages it once it is driven into new content (S2.25's operator log hit its first miss at `frame 4511 (151.31 s)`). Two 200 s boots, with and without `build/shader-libs`, logged `0 scans … 0 waits totalling 0.0 ms`: the waits are zero because the path never ran, not because prebuilt libraries removed them. A line gated on a counter that may never advance must also be emitted at a point the boot always reaches (here, warm-up end), and an empty log is a zero only once the counter it is gated on is known to have advanced.

26. **Do not register an SDK IPC service family the guest never asks `sm` for.** S3.1c registered `savedata` and `ns:save_data` on the assumption the save round-trip ran through them, and S3.1d's seed required the read "through the savedata service"; the game's `main.patched.bin` imports only `nn::fs::MountSaveData` and `nn::fs::EnsureSaveData` and **no `nn::ns` symbol**, and a windowed boot to the main menu opens the family zero times — the round-trip runs on the `nn::fs` `save:` mount. A registered family the guest never opens is dead code whose handlers no run can exercise, and a seed that names it as the path sends the next session to the wrong file. Read the game module's own imports, or the `sm` opens in a log, before building the family it would use.

27. **Do not pass a pad bit to the `key` schedule command.** `runtime/input.c:160` accepts `key <code> <ms>` only when `code < 128`, and the guide's key map — "Return→1024, 38→1, …" — lists the pad bits `button()` produces, not the codes the file takes, so `key 1024` meant to press ⊕ was rejected with `FAIL: invalid diagnostic input command` and killed the run at 28 s with no screenshot. ⊕ is `key 36` (Return's keycode) and Ⓐ is `key 38`; 1024 is what 36 becomes in the pad, not what the file takes.

28. **Do not arm a diagnostic that writes files without creating its output directory first.** S3.3b's third boot set `DM_NVN_TEXDUMP=<dir>/f-%d.png` where `<dir>` did not exist: the dump armed, counted 46 colour targets, logged its frame, and every PNG write failed on the missing directory — so a 40 s run that reached the race left no images, and the next boot had to be spent to get the same frame. `screenshot`/texdump open the path they are given and do not create it. `mkdir -p` in the runner before the launch, not after the run reports nothing.

29. **Do not count the pass dump's draw records by the wrong letter.** The per-draw line is lowercase `d` (`d <pass> bv=… fs=… vc=…`) and uppercase `D` is a different record — the bloom-chain note and the `prim=` summary. S3.3b's first pass reader counted `D`, which made pass 549789 — 330 draws, 2,032 texture binds, the pass that draws the whole scene — read as a single fullscreen draw, and the same reader put 114 "draw groups" in a 120-pass frame. Counting the wrong letter does not error; it makes the pass that matters look like it drew nothing, which is the opposite of the fault being hunted.

30. **Do not read a black shaded target as a zero in the shading math before the draws that write it have been shown to rasterize.** S3.3b spent a whole slice concluding "the fault is the shading stage" from one race frame whose shaded targets held their clear colour while the G-buffer beside them carried the world's textures. The shader was never the fault: every back-face-culled draw in that frame was culled on the *wrong face*, because NVN names the front face with y up and Metal evaluates winding with y down, so mapping `NVN_FRONT_FACE_CCW` to `MTLWindingCounterClockwise` literally puts the visible surface on the back. The G-buffer looked like proof that the same surfaces were being drawn; it was proof only that the *unculled* draws ran. One `TOTK_GPU_WINDING_FLIP=1` run moved ser12/ser14/ser15 from exactly 0 to (78–100) and the frame from black silhouettes to a lit race. Read each draw's `cull=` and the frame's `front=` against the target before reading its shader, and keep the flip switch as the one-run test.

31. **Do not read `[totk-fs] read <path>` as a read that happened.** The line is emitted by `open_file` (`games/nfs/runtime/fs_host.c:203`) *before* the `stat()`, so it records the attempt, not the result: three S3.3c boots with an empty profile directory each logged `read save:/MUD64.8` at ~62 s while the file did not exist, and the open then failed with `R_PATH_NOT_FOUND` and the game showed the EA User Agreement. A `write` line is the same — it marks an open for writing, and S3.3a's four `write save:/MUD64.8` opens left the mtime unchanged. Confirm an open by the file's size/hash/mtime or the handler's result, never by the log line alone; the same rule makes a "reads the save" claim rest on the bytes the boot consumed.

32. **Do not read `window closed; graceful guest shutdown pending` as a shutdown the guest gets to finish.** `frontend.m`'s `windowWillClose` polls `runtime_fs_save_busy()` only while a save is already in progress (15 s), and otherwise prints that line and calls `_exit(0)` immediately — so the `close` input command ends the process and gives the game no chance to write anything. S3.3c's first three-boot run ended every boot this way and wrote nothing; a save has to happen while the guest is running, as it did at menu entry after the agreement was accepted. When a run must produce a write, drive the guest to the trigger and hash the file while it runs, not on the way out.

33. **Do not ship a launcher without `DM_PRESENT_LINK_FALLBACK=1`.** The NFS app's first packaged run stopped presenting at frame 610 the moment the terminal took focus: the process stayed alive, `wshot` wrote nothing and no key produced a new frame, which reads exactly like a hung game. `DM_PRESENT_LINK_FALLBACK=1` — set by both the TOTK and the BY3 launcher — keeps presents coming when macOS pauses the display link for a window it thinks is covered. A new launcher carries that switch with the rest of the environment, not just the profile and GPU ones.

34. **Do not let a generated header carry a build-machine path into a bundle.** `scripts/prepare_runtime.py` wrote the shared-font rows as `<work>/extracted/firmware/shared-fonts/<name>`, so the packaged `nfs-native` held `/Volumes/X9BS/externalTmp/…/nfs-app/…` six times. Nothing failed while `TOTK_SHARED_FONTS` was set, and the day it was not set the app would have read this machine's work folder for its fonts — the dev-tree dependency the packaging slice exists to remove. The rows are relative to the runtime's working directory now (the work tree in a dev boot, `Contents/Resources/nfs` in the app). Check a new bundle with `strings <binary> | grep <build path>`: 0 hits is the claim.
